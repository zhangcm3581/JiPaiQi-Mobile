# 0.4.24 连续局本地验证 · 2026-09-13

结论：已在本地复现“第一局7份，后续仅1份”的外部表现，但需要人为让6个客户端同时漏采结束和发牌前过渡画面。无法证明现场6个客户端当时也是这个原因。生产服务未修改，运行代码未修改，未发布新APK。

## 验证方法

将此前原生Vision从真实录像取得的2202个采样（8局，840宽）回放到当前RoundSession与7条真实本地WebSocket连接。每条连接按序收发消息，覆盖先处理一人的结束、其他人再结束的时序。第一个客户端使用录像识别手牌，其余6个使用牌堆补集构造合法手牌，因此不是7台模拟器同时进行图像识别。结果是否生成作为7份收齐的证据，返回数量检查13张。

本地运行命令：

```sh
bash scripts/verification/check_video_state.sh
JPQ_REPLAY_MODE=miss-six bash scripts/verification/check_video_state.sh
JPQ_REPLAY_MODE=gap-six bash scripts/verification/check_video_state.sh
JPQ_REPLAY_MODE=miss-boundary-six bash scripts/verification/check_video_state.sh
```

最后一项为复现用例，应失败退出；其余通过。脚本限定127.0.0.1，使用独立数据库。

| 场景 | 结果 |
|---|---|
| 正常原生识别轨迹，7客户端异步结束 | 8局均计算结果 |
| 6客户端不识别结束，保留过渡画面 | 8局均计算结果 |
| 6客户端结束期间截图中断，保留过渡画面 | 8局均计算结果 |
| 6客户端结束及发牌前过渡期间均无采样 | 仅第一局计算结果；后续仅1客户端上传 |

最后场景中6客户端一直处于“服务端已换轮，等待本机真实结束”。数据库仍保留的第4—8局均只有1份手牌。

## 原生识别验证

MuMu安装的0.4.24使用现有原生测试，3项通过：8手牌在840/1600两种尺寸逐牌核对；旧模板身份校验；开局、摆牌、比牌和结束特征。测试仅使用缓存解压素材，不更改用户配置，不连接生产服务器。

## 已定位的限制

0.4.23/0.4.24的备用跨局恢复要求服务器已换轮后，本机连续观察到600毫秒非开局、非结束画面，然后出现不同于上一局的完整13张手牌。若结束和过渡都漏采，needsHands不会重新开启，后续新手牌也不参与判断，因此可持续停留旧局。单纯漏结束的修复不足以覆盖这个条件。

不能直接把服务器换轮当作允许重复提交旧牌。后续修复需要专门验证在缺少过渡帧时，如何用新的完整手牌证据恢复，同时防止旧局牌或不稳定识别被当作下一局。现场是否因遮挡、采集间断或其他原因漏过渡仍未知。
