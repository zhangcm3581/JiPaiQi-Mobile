# 手牌数字与花色独立验证（2026-09-10）

本规范属于客户端识别契约。JPQ Tools、导出的素材包和 Android 客户端必须一致实现；不能只用整幅模板的最高相关分数确定花色。

## 修复原因

真实录像第 4、7 手牌的黑桃 6，以及缩放后的第 6 手牌，出现了“仍识别 13 张但花色错误”。52 个原模板的标签检查正确。数字面积大，整幅相关系数会让数字的高分掩盖小花色的不符。只有张数检查、连续两帧和整幅阈值，都不能纠正稳定的花色误判。

## 必须实现的顺序

1. 手牌场景和模板先统一白/黄底：BGR 中 `B = max(B, min(G, R))`，G、R 保持原值。状态按钮不使用该处理。
2. 根据素材配置执行彩色/灰度/二值化预处理。当前十三水手牌使用彩色，内置包 1.3.0 阈值 **0.80**（旧包 1.2.0 为 0.85）；状态图片仍为彩色 **0.9**。
3. 为降低整片搜索的开销，将预处理后的场景和模板转成灰度，用 `INTER_AREA` 缩到 0.5 倍。使用 `TM_CCOEFF_NORMED` 找候选；候选阈值 `min(0.65, 配置阈值)`。这一步仅定位，不决定牌面，也不直接上报。
4. 候选位置乘 2，四周各留 4 个原图像素，在原始预处理后的彩色图中重新匹配完整模板。完整模板分数必须达到配置阈值。
5. 模板高 H，分界 `floor(H × 0.62 + 0.5)`。上部为数字，下部为小花色；分别对同位置的原图区域做 `TM_CCOEFF_NORMED`。**两个分数各自都必须达到素材包配置阈值**。该分界针对“上数字、下小花色”的现有角标裁图格式。
6. 候选最终分数为两个分数的等权平均。同一位置不同牌面按此分数竞争；重叠超过较小框面积的 50% 时只留一个候选。相邻重复牌分别保留。无匹配的牌不得自动补全。
7. 客户端只在开局按钮命中、未命中结束特征、且本局尚需手牌时识别手牌；其他阶段仍采样和识别状态，不停止脚本。Tools 的单图手牌测试仍可单独识别，不依赖状态按钮。
8. 只有连续两个有效采样得到相同的 **13 张合法点数、花色及重复数量**，并完成本轮绑定，才可上报。12 张、14 张、某牌出现第 3 份、非法点数/花色、两帧结果不同均不能上报。结束候选、缺帧、打开设置等会中断未完成的连续确认。

## 素材包与兼容

素材包版本 1.2.0 起，`requires` 含 `cards.hand_rank_suit.v1`，每个手牌检测器的 `params.identity_scoring` 为同名标识。旧客户端必须拒绝未知能力，不能悄悄忽略。

新版 Android 客户端读取以前已经启用白黄底统一的素材包时，也自动执行这套数字/花色验证和候选定位；无需为了升级重置租户 ID、客户端 ID 或原搜索区域。包1.2.0另增加灰/绿“两对”按钮作为摆牌状态补充；旧包的自动升级保护及搜索区见 [轮次时序](round-sync.md)。状态按钮的搜索区域、阈值和判断方式不变。

场景预处理缓存只在当前帧内复用，键包括区域、预处理模式和底色处理；帧结束释放，不能跨帧复用旧画面。仅在截图线程运行，不卡住 UI 线程。

## 验证依据

`FullVideoAuditTest.eightDealsMatchEveryCardAtBothResolutions` 使用从原录像按帧索引顺序解码、人工逐张标注的 8 手牌，在 840×474 和 1600×900 下核对完整牌面。预期结果不从原识别报告抄录。真实 MediaProjection 流程另测试 12/14 张的拒绝上报及合法 13 张的实际服务端入库内容。完整录像通过原生识别、RoundSession 和真实 RoundSocket 另行回放。

0.4.16 常规采样目标为 0.2 秒；已看到开局且尚需手牌时短暂使用不高于 80ms 的采样目标，确认后恢复常规周期。首帧完整手牌参与两帧一致性校验，不额外浪费第三帧。若某帧处理较慢，只取最新截图；不能积压旧帧，也不能用重复的缓存帧凑两次确认。实际耗时与设备有关，测试报告给出本机测量值。
